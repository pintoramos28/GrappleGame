# Story 1.7: Zip-Pull Within a True Maximum Grapple Boundary

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want grappling to accelerate me toward an anchor while preserving freedom inside its maximum range,
so that grappling builds useful momentum without behaving like a fixed-length rope.

## Acceptance Criteria

1. **Attachment commit (AC 1).** Given the current physics-step targeting result contains a valid accepted target seed, when the player's grapple request is committed, then the player-owned grapple controller creates one active attachment using the authoritative anchor position and the resolved immutable `GrappleDefinition`; and the grapple remains simulation-owned and active until release, invalidation, cancellation, or another defined terminal reason.

2. **Acceleration-based pull (AC 2).** Given a valid static grapple is active, when the player motor resolves sustained influences, then the grapple controller submits the authored acceleration profile directly toward the current anchor through the sustained-influence phase; and the grapple controller does not assign body velocity, call movement, or discard pre-existing momentum.

3. **No constraint inside the boundary (AC 3).** Given the player is closer to the anchor than `max_grapple_length_m`, when movement would remain inside the maximum boundary, then the maximum-distance constraint makes no correction; and inward, outward, and tangential movement remain available subject only to the other authored motor influences and caps.

4. **Attachment distance is not rope length (AC 4).** Given the player attaches to an anchor at 10 metres while the validation definition has a 35-metre maximum grapple length, when the player subsequently moves away from the anchor, then the player can move beyond the original 10-metre attachment distance until reaching the authored 35-metre boundary; and the attachment distance is never stored or interpreted as a fixed rope length.

5. **Outward-only clipping (AC 5).** Given the player is at or would cross the maximum grapple boundary, when the motor resolves constraints and redirections, then only the outward radial component that would carry the player beyond `max_grapple_length_m` is clipped or redirected within documented tolerance; and inward movement, anchor-directed pull, and tangential movement remain unrestricted by that boundary.

6. **Overshoot correction (AC 6).** Given the player approaches the maximum boundary at high outward velocity, when a normal physics step would overshoot it, then the motor prevents or corrects the small numerical overshoot within the documented positional tolerance while preserving valid tangential and inward velocity; and the correction does not snap the player to the anchor, zero all momentum, or perform an additional movement commit.

7. **One range authority (AC 7).** Given the current slice uses a resolved `max_grapple_length_m` of 35 metres, when acquisition and active constraint behavior are inspected, then both consume the same value from the same immutable `GrappleDefinition` authority; and no player scene, targeting code, active attachment, presenter, or disposable tutorial content maintains a competing acquisition or tether-range scalar.

8. **Momentum-preserving release (AC 8).** Given the grapple button is released in the current `PlayerCommandFrame`, when the grapple controller terminates the attachment, then sustained pull and maximum-distance constraint submissions stop for that same simulation step according to the declared release phase; and the player retains the velocity resolved at release without an artificial stop, snap, or replacement launch velocity.

9. **Exactly one reason-coded terminal (AC 9).** Given the player dies, the attachment becomes invalid, the owning state is cancelled, or another defined terminal condition occurs, when grapple termination is requested one or more times, then exactly one reason-coded terminal result is committed and grapple-owned motor submissions are removed safely; and repeated termination calls do not repeat state transitions, presentation effects, or cleanup.

10. **Occurrence-local resolved values (AC 10).** Given grapple acceleration, speed limits, maximum length, or other authored values are resolved for an execution, when runtime modifiers or state-specific values are needed, then the controller computes occurrence-local resolved values without mutating the shared `GrappleDefinition`; and a later grapple starts from the unchanged authored definition.

11. **Presentation follows simulation (AC 11).** Given the grapple line, reticle, camera, audio, or development diagnostics present an active grapple, when the player moves inside or along the maximum boundary, then presentation follows the authoritative attachment and motor snapshot; and presentation geometry, animation, or audio cannot apply pull, enforce distance, release the grapple, or determine the terminal result.

12. **Read-only attachment diagnostics (AC 12).** Given grapple diagnostics are enabled, when an active attachment is inspected, then the snapshot reports attachment identity, anchor position, current distance, maximum distance, range fraction, pull direction, submitted acceleration, radial and tangential velocity, any boundary correction, and terminal reason; and diagnostics are read-only and do not recalculate or alter constraint resolution.

13. **Focused real-Jolt integration suite (AC 13).** Given the focused real-Jolt grapple integration tests run, when they exercise attachment well inside the range, attachment near the boundary, outward travel from a short initial distance, inward travel, tangential travel, high-speed overshoot, release, death cancellation, and duplicate termination, then the grapple behaves as an acceleration-based zip-pull with a maximum-only boundary and preserves valid momentum within documented tolerances; and equivalent real-time scenarios at shipping 60 Hz and diagnostic 120 Hz produce equivalent attachment duration, acceleration, boundary behavior, and release velocity within documented tolerances.

14. **Story completion gate (AC 14).** Given Story 1.7 is complete, when the traversal smoke procedure and working-tree diff are reviewed, then static-target grappling uses the semantic motor pipeline, the validation definition enforces the same 35-metre acquisition and active boundary, release preserves useful velocity, retained UIDs remain valid, and the launch scene remains runnable; and the story has not implemented moving-anchor sampling, target discontinuity handling, rope wrapping, rope elasticity, reeling, rope-segment simulation, final grapple presentation, tutorial preservation, or unrelated migration.

### Zip-Pull and Maximum-Boundary Semantics (locked)

- **Zip-pull is acceleration, not velocity.** The authored profile is `48 m/s^2` initial decaying at `53.333333 m/s^3` to an `8 m/s^2` floor (floor reached at ~0.75 s), with a `22.0 m/s` total-speed cap (GDD Movement Feel Table; `grapple_definition.tres`). Existing momentum is preserved by construction because pull integrates into velocity through `submit_sustained_acceleration`. Do not redesign the profile; Story 1.7 only changes where its values are read from (Task 1).
- **One range, two consumers.** `GrappleDefinition.max_grapple_length_m = 35.0` governs acquisition (Story 1.6 resolver predicate, inclusive quantized `<= max_grapple_length_m`) and the active tether boundary (this story). `acquisition_tolerance_m = 0.005` remains a classification/quantization tolerance only and is never a range.
- **Attachment distance is never rope length** (AC 4; architecture worked example: "attaching at 10 m does not create a 10 m rope"). Nothing may store or infer a tether length from the attachment distance.
- **Constraint rule.** Inactive while `d < max_grapple_length_m`. At the boundary, clip or redirect only the outward radial velocity component (away from anchor) that would cross it; inward and anchor-directed pull are unrestricted; tangential motion is unrestricted (AC 3, 5).
- **Overshoot rule.** A high-speed step that would cross the boundary is prevented or corrected within a documented positional tolerance (AC 6). Document the tolerance and its bound in Completion Notes (suggested magnitude: small fixed physics tolerance on the order of the profile quantization/margin scale, e.g. `<= 0.05 m`; it must never function as range). Correction must not snap to the anchor, zero momentum, or add a movement commit. Note: direct transform writes fight physics interpolation (see Latest Technical Information); if a positional correction is used, apply the existing interpolation-reset discipline and record it.
- **Reference point consistency (hidden trap).** Today pull direction is computed from `_get_player_mesh_center()` while the motor commits from the body transform. Distance reporting, pull direction, boundary math, and diagnostics must all use one documented reference point; a mismatch silently breaks the 10 m -> 35 m scenario and 60/120 Hz equivalence. Pick, document, and test one (AC 4, 13).
- **Release.** Detected on the `PlayerCommandFrame` release edge inside the grappling state update, before motor submission, so pull and constraint submissions stop for that same step "according to the declared release phase" (AC 8). Preserve the exact current ordering; document the declared phase. Committed velocity at release is the player's velocity going forward (no stop/snap/relaunch).
- **Terminal behavior.** Invalid anchor/`is_instance_valid` failure cancels with a typed reason; it never snaps the player (architecture edge-case rule). Death and state cancellation follow the same exactly-once path.

### Attachment Lifecycle and Terminal Contract

- `GrappleAttachment` is player-owned runtime state (mutable), created only after activation validation succeeds, exactly one active at a time. It carries a stable execution/attachment identity for diagnostics, dedup, and terminal attribution.
- Lifecycle: accepted seed -> committed attachment (active) -> exactly one reason-coded terminal (release | invalidation | death | cancellation | documented additional reason) -> submissions removed. Held grappling needs no fixed active duration (architecture hold rule); continuation is simulation state, never presentation.
- Termination is idempotent: duplicate calls return the already-committed terminal result without repeating transitions, signals, presentation effects, or cleanup (NFR15; mandatory contract-suite item).
- Signals, if used, are past-tense committed facts emitted after state commit (e.g. `grapple_ended(reason)`); per-step data flows through read-only snapshots, not per-step signals. Subscriber order must not matter.
- Occurrence-local resolution (AC 10): resolved values live on the attachment; the shared `GrappleDefinition` and `GrappleTargetResponse` are read-only during play. `definition.max_grapple_length_m *= x` is the documented anti-pattern. A later grapple must start from the unchanged authored definition.

### Diagnostics Contract (AC 12)

Snapshot fields, all scalar copies / stable IDs: attachment identity; anchor position; current distance; maximum distance; range fraction; pull direction; submitted acceleration; radial velocity; tangential velocity; boundary correction (none or bounded record of what the constraint did); terminal reason. Rules: development-only, opt-in, read-only, bounded; no duplicate computation (no re-querying physics, no recalculating constraint resolution); absent/disabled in release-like runs (NFR19, FR58). The existing `GrappleTargetingDiagnosticSnapshot` covers acquisition; this story adds the attachment-side snapshot beside it. Keep expected gameplay outcomes out of `GameLog` error/warning paths (release, normal rejection, boundary clipping are not errors).

### Latest Technical Information

- Pinned engine Godot 4.7.2-stable; no upgrades. Use the 4.7 doc tree for version-specific behavior.
- `CharacterBody3D` (https://docs.godotengine.org/en/4.7/classes/class_characterbody3d.html): `velocity` is meters per second and is modified by `move_and_slide()`; the common mistake is storing `velocity * delta`. `move_and_slide()` must be called from `_physics_process()` (it uses the physics step delta internally) and may recompute velocity across up to `max_slides` (6) slides; `get_real_velocity()` reflects actual post-slide motion while `velocity` reflects the requested motion - be explicit about which velocity the diagnostics snapshot reports (AC 12) and keep tests tolerant (NFR6).
- Physics interpolation (project-wide, enabled): interpolation blends per-physics-step transform snapshots at render rate. Direct transform writes outside the physics step (or mixed with `move_and_slide()` on the same node) produce conflicting snapshots and visible jitter; if the overshoot correction writes position, it must happen in the physics step and use the established `reset_physics_interpolation()` discipline (as the frozen rope spec does), never from `_process()`. Authoritative gameplay stays in `_physics_process(delta)`; `_process` is presentation-only (project-context rule).
- Jolt Physics: keep assertions tolerant; boundary math should use stable tolerances rather than exact equality; swept/velocity-aware reasoning applies to high-speed traversal (NFR6).
